01 / Introduction

Start here

Learn the difference between the products and give your first request a useful shape.

01Chat & researchChoose the right starting point3 min+

Begin with the kind of result you want. A conversation, a generated image and a completed task need different interfaces. Choosing that first removes a surprising amount of friction.

  1. Name the outcome

    Write down the thing you want to have at the end: an explanation, a source-linked brief, a visual, a code change or a recurring report.

  2. Match the working surface

    Use chat for a conversation; Imagine for generated media; Build for a coding workflow; Bot for work across tools. Developers can assemble their own experience through the API.

  3. Set a finish line

    Describe how you will judge the result. A five-bullet summary with links is easier to assess than a request to tell you everything.

Your finish line

You can explain which product you chose and what a successful result will look like.

An original starter prompt

Help me choose the right Grok product for this outcome: [describe the result]. Explain the inputs I need, the interface to start with and one concrete way to check the result. Ask about missing context before recommending a workflow.

Grok product overview (opens in a new tab)Grok Bot overview (opens in a new tab)Grok Build guide (opens in a new tab)
02Chat & researchWrite a brief that finishes well4 min+

A strong request makes the goal and the deliverable visible. Add relevant context, practical constraints and an output format, then give the model room to ask about anything that would change the answer.

  1. Lead with the job

    Say what you want done and who the result is for. Include a document, a source link or an example of the quality you expect.

  2. Add the boundaries

    Specify the scope, the date range and any decisions already made. Leave personal details out of a public example.

  3. Specify a useful return

    Ask for the answer in a form you can inspect: a comparison, a draft, a checklist or a proposed change with a validation plan.

Your finish line

Someone reading the request can identify the goal, inputs, constraints and expected output without guessing.

An original starter prompt

Outcome: [what I want to achieve]. Context: [relevant facts or attached material]. Constraints: [scope, time, things to preserve]. Return: [format and length]. Before starting, ask only for missing information that would materially change the result. Label assumptions.

Grok product overview (opens in a new tab)
03Chat & researchCheck the answer before using it4 min+

Treat the first result as something to inspect. A fluent explanation can still mix a fact with an interpretation. Ask the model to make that distinction visible and reopen the material that matters.

  1. Check a specific claim

    Pick the date, number or quote that matters most. Open its linked source and find the passage that supports it.

  2. Ask for uncertainty

    Have the model separate documented facts, its own inference and unresolved questions. Missing evidence should remain visible.

  3. Revise the brief

    If the answer misses the point, name the exact change you need and preserve the parts that worked.

Your finish line

At least one important claim has been traced to its source, with the publication date and scope checked.

An original starter prompt

Audit the answer above. Separate supported facts, interpretations and open questions. For each important factual claim, give its original source and date if available. Identify any statement that the linked material does not actually establish, then revise that statement.

02 / Beginner

Get useful results

Practice research, visual direction and voice with a clear way to judge the result.

04Chat & researchBuild a brief from current sources6 min+

A useful research brief answers a decision rather than collecting links. Choose a tight question and a time window, then ask for original announcements, filings or documentation where those exist.

  1. Define the question

    For example, ask what has changed in the last month and how those changes affect a particular owner, developer or reader.

  2. Request current evidence

    In a search-capable experience, ask for source retrieval explicitly. Distinguish the date an event happened from the date an article discussed it.

  3. Inspect the synthesis

    Read the supporting pages for the main conclusion. Keep an announced target separate from a shipped feature or a confirmed delivery.

Your finish line

The brief includes original links, dates, a clear conclusion and a list of gaps worth following up.

An original starter prompt

Research [specific question] for [audience] using current sources within [date range]. Prioritise original announcements and documentation. Return a short conclusion, a table of what changed with event and publication dates, links for key claims and unresolved questions. Distinguish announced plans from available products.

Web Search tool (opens in a new tab)Official model catalogue (opens in a new tab)
05ImagineDirect an image or a short scene5 min+

Think like an art director. Subject, composition and lighting give an image a readable structure; a video also needs a deliberate action and camera movement. Start with one clear visual idea.

  1. Describe the frame

    Name the subject, environment, viewpoint and aspect ratio. Explain where the eye should go first.

  2. Add one visual direction

    Choose a lighting mood, material treatment and color palette. Avoid a long list of competing styles.

  3. Refine one variable

    Compare versions by changing a single element. For an edit, state which parts of your reference must remain consistent.

Your finish line

The brief communicates the subject, composition and intended visual treatment before technical effects.

An original starter prompt

Create a visual concept for [subject]. Composition: [viewpoint and focal point]. Setting: [environment]. Lighting: [mood and direction]. Palette: [colors]. Format: [aspect ratio]. Preserve: [important details]. For a video version, use one coherent action and describe a restrained camera movement.

Imagine API overview (opens in a new tab)
06VoiceMake voice a useful back-and-forth5 min+

A spoken conversation works best with a role and a rhythm. Choose a short exercise, say how feedback should be delivered and ask for one question at a time so the session stays manageable.

  1. Pick the exercise

    Use a mock interview, language practice or an explanation of an unfamiliar topic. Tell Grok your starting level.

  2. Control the pace

    Ask for short turns and time to answer. Tell it when you want a hint or a simpler explanation.

  3. Finish with a review

    End with a recap of what improved and the next thing to practice. Verify important factual details against a written source.

Your finish line

The conversation has a clear pace, a stopping point and feedback you can act on.

An original starter prompt

Act as my practice partner for [topic or situation]. My starting level is [level]. Ask one short question at a time and wait for my answer. Give specific feedback after each response. After five turns, summarise two strengths and two practical improvements.

03 / Intermediate

Work with context

Bring in files, a project or a focused Bot role and make the output reviewable.

07Chat & researchTurn a document into a decision aid6 min+

Choose material you are entitled to use and tell Grok what to extract. A decision log, a comparison or a set of unanswered questions is often more useful than a generic summary.

  1. Choose the evidence

    Attach the relevant file or provide the source in a supported interface. Explain whether it is complete and which sections matter.

  2. Make extraction traceable

    Ask for a section, page or cell reference for each key item where the format allows it. Preserve units and dates.

  3. Check the difficult parts

    Inspect footnotes, ambiguous tables and missing pages. Tell it to flag unavailable information instead of inventing a value.

Your finish line

You can trace the extracted decisions and numbers back to the material you supplied.

An original starter prompt

Using the attached document, produce a decision log with columns for decision, supporting passage or page, owner, date and open question. Preserve the source units and wording for important figures. Mark missing information explicitly and do not infer an owner or deadline that is not stated.

Grok product overview (opens in a new tab)
08BuildTake a bug from symptom to review7 min+

Give a coding agent the observed behavior, the expected behavior and a way to reproduce the gap. A focused brief lets it investigate before changing the project and gives you something concrete to review.

  1. Show the failure

    Supply the error, input and relevant environment. Ask it to identify the entry point and read the existing conventions.

  2. Agree on a check

    Describe a reproducible example or a behavior test. A meaningful test should fail for the reported bug and pass for the intended behavior.

  3. Review the resulting change

    Ask for a concise explanation of the cause, the files changed and the validation result. Inspect assumptions before publishing.

Your finish line

The proposed fix has a reproduction, a focused diff and a recorded validation result.

An original starter prompt

Investigate this defect: [symptom and reproduction]. Expected behavior: [expectation]. Read the relevant code and project instructions first. Explain the likely cause, implement a focused fix and run an appropriate behavior check. Return the changed files, test results and any unresolved limitations. Prepare a reviewable change before publishing.

Grok Build guide (opens in a new tab)Grok 4.7 model reference (opens in a new tab)
09BotCreate one Bot with a clear job7 min+

Give a Bot a stable responsibility rather than every task at once. Describe the job, the sources it should use and the output you want to receive. Start with a one-time assignment before adding automation.

  1. Set up the role

    Install the official app, sign in and confirm your eligible access. Create a Bot with a short name and one primary responsibility.

  2. Connect useful context

    Use a supported connected app when available, or take over its computer for a necessary sign-in. Keep credentials out of ordinary prompt examples.

  3. Inspect the first delivery

    Choose a small research or drafting task. Ask for links, assumptions and a clear point where further action needs your review.

Your finish line

The Bot has completed one scoped task using the intended sources, and its standing role is understandable.

An original starter prompt

Your role is [focused responsibility]. Use [approved source systems] to prepare [specific deliverable] for [audience]. Preserve source links and identify missing inputs. For this first run, prepare the result in this conversation and wait for review before contacting anyone or publishing changes.

04 / Advanced

Build a repeatable system

Define an integration, save a reliable method and schedule it with explicit failure handling.

10APISpecify an API workflow before building8 min+

An integration needs more than a model name. Define the input, expected output, tools, failure behavior and budget. Treat latency and task quality as things to measure with your own examples.

  1. Choose the interface

    Identify whether the job needs text, generated media, speech or current search. Check the corresponding model and tool documentation.

  2. Define the contract

    Specify an output schema and how your application handles missing evidence, malformed responses, timeouts and retries.

  3. Create an evaluation set

    Use representative inputs with expected outcomes. Measure quality and cost together, keeping credentials on the server.

Your finish line

The integration has an input/output contract, a small evaluation set and explicit failure behavior.

An original starter prompt

Design an API workflow for [use case]. Specify inputs, output schema, candidate models or tools, server-side credential handling, failure modes, retry rules and a small evaluation dataset. Use current official documentation for availability and pricing. Separate token costs from search, media and other charges.

11BotSave the method that worked6 min+

Once a task reliably produces the right result, turn its method into reusable instructions. Capture why each step exists and how to validate it so the process survives a slightly different input.

  1. Capture the sequence

    List the inputs, source systems and decisions made during the successful run. Keep the result format explicit.

  2. Add edge cases

    Explain what should happen when a source is missing, a value is ambiguous or the expected result is empty.

  3. Test a new example

    Run the saved skill on a different safe input and inspect the result before using it as a recurring process.

Your finish line

A second input produces the intended result without relying on an unstated assumption from the first run.

An original starter prompt

Turn the process we just validated into a reusable skill called [name]. Include when to use it, required inputs and access, the work sequence, decision rules, output format and validation. Add explicit behavior for missing or stale data, and preserve the review boundaries we agreed.

Skills and routines (opens in a new tab)
12BotSchedule a routine you can trust8 min+

A routine should make repeated work easier to inspect. Start from a tested skill and choose a clear schedule, input source and place for the result. Decide what happens when the job cannot finish.

  1. Define ownership and time

    Choose the owning Bot, the time zone and the schedule or supported trigger. Make the scope narrow enough to avoid irrelevant runs.

  2. Specify success and failure

    Name the current source, expected output and completion signal. Ask it to report missing input rather than quietly reuse an old result.

  3. Run and inspect once

    Check the first run and the effect of its actions. Revisit the process when a source, website or connected tool changes.

Your finish line

The routine has a clear owner, schedule, current input, output destination and failure message.

An original starter prompt

After we validate [skill name], run it [schedule and time zone] using [current source]. Return [format] in this conversation with the source timestamp and run outcome. If a required source is missing or stale, report that failure and stop. Keep [specific consequential actions] for my review.

How are Grok, Bot, Build and the API different?

Grok is the consumer assistant. Imagine and voice provide media experiences. Bot adds a persistent teammate and computer; Build is a coding agent. The API lets developers build their own interfaces. A capability or model listed for one surface is not a guarantee of access in every other surface.
